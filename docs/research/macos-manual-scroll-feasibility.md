# macOS manual scroll capture: feasibility research (issue #14)

## Status and scope

**Research only; feasibility is not established.** No prototype or real-device experiment was performed. This note addresses [#14](https://github.com/Wade11s/ArcShot/issues/14) in the context of the [#11 resolution](https://github.com/Wade11s/ArcShot/issues/11#issuecomment-6476055780): a previously selected rectangle, user-driven vertical scrolling in both directions, verified-only stitching, and a small preview that may overlap the selection. The test environment is the user's MacBook Air built-in display only. This is not a recommendation to change that workflow, select a product design, or promise compatibility with arbitrary apps. OS version, MacBook Air model, display mode, target apps and distribution/sandbox configuration are not specified and must be recorded in testing.

**Evidence labels:** documented = what the cited owner says; hypothesis = an implementation path to investigate, not a platform guarantee; test = mandatory device evidence; boundary = when #11 requires stopping or not starting. All thresholds, matching methods and API combinations below are experimental, not product decisions.

## Documented platform capabilities and their limits

- Apple describes ScreenCaptureKit's `SCStream`, shareable content, display/window filters and configurable output, delivering `CMSampleBuffer` samples. A complete status denotes a new frame; idle means no new surface, not necessarily an error. Screen capture requires user consent. [Apple, Meet ScreenCaptureKit](https://developer.apple.com/videos/play/wwdc2022/10156/).
- Apple demonstrates a display filter excluding an app or individual windows, and a source rectangle, output dimensions, cursor control, and per-frame content rect, content scale, scale factor and dirty rects. Its single-window filter captures the window even when occluded, but excludes child/pop-up windows; a minimized window's output pauses. The fixed-sized output can scale a resized source. [Apple, Take ScreenCaptureKit to the next level](https://developer.apple.com/videos/play/wwdc2022/10155/). These statements do **not** establish that every arbitrary selected display rectangle corresponds to one window, nor that an excluded preview reveals correct pixels in every composition case.
- The configured minimum frame interval limits the maximum delivery rate, not a guarantee of every intermediate state. Apple describes buffer-pool starvation and frame loss if surfaces are held too long; queue depth trades memory and latency. [Apple, advanced session](https://developer.apple.com/videos/play/wwdc2022/10155/). Dirty rects describe changed output areas, not proof of scroll direction, displacement, or content identity.
- A window can be transparent to mouse events via `ignoresMouseEvents` [Apple, NSWindow](https://developer.apple.com/documentation/appkit/nswindow). This is all mouse events, not a documented scroll-only pass-through. An AppKit global event monitor observes systemwide events but cannot modify them; key monitoring is subject to permission [Apple, NSEvent](https://developer.apple.com/documentation/appkit/nsevent) and [global monitor](https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents(matching:handler:)). It alone cannot consume Enter or clicks.
- Apple distinguishes keyboard input monitoring permission for a listen-only event tap from Accessibility authorization for a modifying tap or synthetic input, in its Catalina security presentation. Tap creation may fail or omit unauthorized event types; test actual effective access rather than assuming that a successful prompt or creation grants all events. [Apple, macOS security](https://developer.apple.com/videos/play/wwdc2019/701/); [CGEvent tap creation](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsofinterest:callback:userinfo:)). Exact requirements and sandbox/distribution behavior for the eventual build and OS remain to be verified; Apple Events automation is a separate permission and is not implied by an event tap.
- Trackpad and mouse input are not interchangeable: Apple documents precise vs coarse scroll deltas and momentum phases [precise deltas](https://developer.apple.com/documentation/appkit/nsevent/hasprecisescrollingdeltas?changes=__5), [momentum](https://developer.apple.com/documentation/appkit/nsevent/momentumphase). Deltas are input intent, not measured image movement: app response, acceleration, inertia, scroll boundaries, nested panes and asynchronous rendering can differ.

## Capture and preview: candidate paths, not established solutions

1. **Display stream with ArcShot windows excluded**: obtain the single built-in display, explicitly exclude every ArcShot capture/preview window or app as appropriate, configure a native-pixel region or crop consistently, and compare frames. Apple documents exclusion but does not in the cited text guarantee correct underlying target pixels for all excluded overlays, protected content, compositing, transparency or window types. **Test** the right/left outside-selection and overlapping-bottom-right preview placements with a moving, identifiable target; compare pixel-for-pixel against a simultaneous independent reference or controlled ground truth without the overlay. Include the whole excluded footprint, edges, translucent/shadow regions, window recreation, and target updates. A no-preview sequential baseline alone is insufficient if content has changed.
2. **Desktop-independent target window stream**: Apple explicitly describes obtaining the full window despite occlusion. **Hypothesis:** map the existing selected rectangle into that one window and crop its captured content; verify mapping against display ground truth. This cannot blindly represent a selection spanning windows, the desktop, or child/pop-up windows; the chosen target must be identifiable, available and geometrically consistent. A target window capture is not equivalent to capturing the selected display composition. Minimized/paused, protected, blank or stale output is not valid content. Do not silently substitute an altered scope.

Both candidates require tests of selection points versus captured pixels, origin/orientation, backing scale, output size, cropping/rounding, contentRect/contentScale and display mode; avoid hidden resampling and verify a known pixel grid. Freeze/monitor selection and target geometry, scale and display identity throughout. On the single built-in display, disconnect => cancel the entire session with error, no partial result, per #11. Cursor, ArcShot controls, foreign popups/notifications, fixed headers, scrollbars and other occluders must not silently enter a stitch. Exclusion of ArcShot does not remove unrelated occlusion or make invisible target content observable. If correctness under the overlapping preview cannot be established, it fails the specified fallback rather than proving the feature feasible.

## Displacement, reverse deduplication and missing frames

The following is a **testable hypothesis**, not a proven algorithm or universal correctness claim:

- Start with a validated initial frame in a fixed pixel coordinate system; maintain a contiguous, verified content interval with a signed origin relative to that frame and provenance for accepted overlaps. Adjacent observed frame pairs need a uniquely supported *vertical translation* on a sufficiently large, informative overlap. Compare multiple spatially distributed regions, residuals and competing offsets; check horizontal shift, scale/geometry changes, independently moving or fixed regions and consistency with already accepted content. Ignore/categorize known UI only if it cannot conceal needed content; otherwise stop. A candidate score alone or a scroll-wheel delta is not proof.
- Repeated patterns, blank areas, sticky/fixed headers, blinking cursors, video, lazy loading, reflow and changing text can make multiple offsets equally plausible or create a convincing false match. Pixels alone cannot distinguish identical repeated instances, so a unique-looking score is not a general proof of true page position. Retain ambiguity as failure, not invented certainty. Compare against controlled ground truth and adversarial fixtures to evaluate any confidence criterion and false accepts; no threshold is established here.
- Map a verified frame to the existing interval. Movement into already-covered coordinates must agree with prior stored content and add **nothing**; append only genuinely new strips at the top or bottom when their boundary and overlap are verified. On reversal, verify every step against the relevant previous content, including turns within overlap, returning through the initial frame, and reaching the opposite frontier. A disagreement, more than one consistent placement, or an unobserved gap ends capture rather than deduplicating by visual similarity alone.
- A dropped or skipped frame is not necessarily a gap in the final content: accept a later frame only if its overlap and placement against verified content remain demonstrably unambiguous. An idle sample is not automatically a dropped frame. If a fast movement jumps beyond verifiable overlap, or the pipeline cannot keep up and continuity cannot be established, stop; do not infer unseen pixels from input events or fill the hole. Missing intermediate frames can also hide transient changes, so passing this test is bounded to the controlled content model, not a proof of arbitrary history.
- Budget frame processing, surface lifetime, full-height image allocation and preview work. Long captures can exhaust memory or encoding limits; choose measurable limits only after testing. Stop before overwriting verified state on resource exhaustion. Preserve only the last independently validated contiguous result.

## Input, focus and permissions: paths to investigate

**Hypothesis A: click-through + scoped modifying event tap.** A nonactivating/click-through overlay could leave the target under the pointer for natural scroll events while a modifying tap consumes the specified clicks and Enter. This trades simple scroll delivery for broad interception: `ignoresMouseEvents` alone also lets ordinary clicks through, violating #11. A listen-only monitor cannot fix that. Check tap installation, event mask, timeout/disable/re-enable, secure-input restrictions, coordinate hit-testing and teardown; never assume all events are captured. Suppressing a double click requires handling the *first* click without leaking it, not waiting for the second; ensure other clicks, drags and their down/up sequences do not reach the target. Global vs selection-scoped behavior, keyboard modifiers and exact double-click recognition are not settled by the sources.

**Hypothesis B: input-receiving overlay + forwarding scroll.** An overlay can consume clicks/Enter locally, but then delivery of original scroll gestures to the intended underlying view/window is unproven. Investigate only supported posting/routing approaches and their permission requirements; preserve precise/coarse deltas, phase, momentum, direction, location and ordering, and prevent feedback loops or duplicate events. Synthetic events may not be accepted like hardware events, may target the wrong nested view or require focus; do not equate a successful post with actual target scrolling. This is routing user input, not automatic scroll control. Neither path establishes compatibility with every target app.

Focus is a separate constraint: target scrolling, overlay controls, Enter, Escape and global shortcut must coexist without inadvertently activating an app, typing in a field, or losing the intended target. Test keyboard focus and pointer location separately, focus changes and app switching; stop when safe interception or target routing is not assured. Verify Screen Recording separately from Input Monitoring and Accessibility, for the selected mechanism and signed/sandboxed build, including grant, deny, revocation, relaunch and recovery. Do not request permissions irrelevant to the chosen tested path as an assumed requirement. Before capture, missing permission or unavailable target => explain, offer settings entry, preserve selection, and require a manual restart after return (#11). Do not bypass privacy or secure input.

## Mandatory real-device validation plan

No rows below have been run. Record Mac model, macOS build, resolution/scale, app/build identity and sandbox/signing, permission state, target/window identity, selection coordinates, exact input device and settings, configuration, timestamps/frame status, accepted offsets/overlap/confidence, stop reason, output and ground truth. Avoid recording sensitive user data. Repeat on the user's actual MacBook Air; these are gates, not evidence already obtained.

| Area | Controlled experiment and pass evidence |
|---|---|
| Geometry and source | Pixel-grid fixture within a known single window; verify crop and edges against reference at actual backing scale; move/resize window and change display mode midstream. Test a selection crossing windows or containing a popup; do not silently claim single-window output equals display composition. |
| Preview | Put unique changing markers underneath every portion of preview; compare capture with independent target ground truth during motion. Test outside-right, outside-left, in-selection bottom-right, preview transparency/shadow, preview recreation and occlusion by another app. Pass only if underlying selected content is correct, fresh, and ArcShot UI absent. |
| Forward/reverse | Use a uniquely numbered pixel fixture with known full expected image; scroll down, up through existing content, beyond starting position, and reverse repeatedly. Verify exact placement, no duplicate rows, missing rows or seams, and correct initial single-frame completion. |
| Ambiguity and change | Blank/repeated identical rows, low texture, fixed/sticky header, moving cursor/scrollbar, animation, lazy loading and reflow. Inject competing offsets and content mutations. Pass means unsafe ambiguity/change is rejected, not that it stitches everything. |
| Loss and throughput | Log sample status and timestamps; intentionally delay processing/hold surfaces and scroll rapidly past an overlap; compare every accepted interval to fixture truth. Test smaller dropped-frame steps that retain valid overlap and larger steps that do not; no silent holes or guessed content. |
| Input | Built-in trackpad (slow, flick/momentum, diagonal, reversal), external wheel if available, pointer over target/preview/outside, nested scroll views, scroll boundaries, focus changes. Instrument target to prove vertical input reaches the intended view, other clicks/drag and the first and second double-click are not delivered, Enter and Esc behave as specified. Test modifier keys, double-click timing, tap disable/timeout and cleanup, and avoid duplicate events. Horizontal/simultaneous horizontal+vertical capture is outside V1; detect or reject when it prevents verification. |
| Permissions/lifecycle | Test separately denied/granted/revoked Screen Recording, Input Monitoring and Accessibility as relevant; restart/settings flow, secure input, target closure/minimization/occlusion, app switch, display disconnect, stream failure and resource exhaustion. Assert specified outcome, no unintended input, no stale frames or automatic partial copy. |
| End-to-end failure | Compare verified partial with reference; force ambiguous overlap, mutation and memory limit. Stop with reason, retain only verified portion, require explicit choice to use incomplete part or abandon; if none usable only abandon. Disconnect is the exception: cancel entire session. Confirm original selection restoration where #11 requires it. |

A controlled fixture can falsify an implementation and quantify a bounded test envelope; it cannot prove uniqueness for arbitrary dynamic applications. Include representative actual target apps only after the fixture, recording app/version and mismatches, with no universal compatibility inference.

## Explicit failure boundaries and open gaps

- No permission, target unavailable, inability to reliably route/intercept required inputs, capture an unoccluded correct selection including beneath preview, or establish stable geometry: **do not start**, or stop if discovered after starting. Do not silently alter selection, target, input behavior or capture scope.
- No unique, consistent vertical placement or sufficient verified overlap; unexplained content change/occlusion, horizontal movement that invalidates registration, missing frames that prevent continuity, target becoming unavailable, stream error or resource cap: **stop and explain**. If a usable verified contiguous result exists, offer explicit use of the incomplete part or abandon; otherwise only abandon. Never silently bridge gaps or automatically copy partial data. Display disconnect cancels the entire session without partial result (#11).
- A static initial frame can be completed without scrolling if it is itself valid; it does not establish page-top/page-bottom coverage. Successful manual completion means end of capture, not completeness of the source document.
- Still unknown: exact minimum supported macOS and concrete API availability; overlay exclusion compositing on the user's machine; target selection and mapping; real-world event routing/focus and permissions under the actual packaging; secure/protected surface behavior; safe confidence thresholds, memory/latency envelope and application coverage. These require the tests above and, where needed, further primary-source API/version verification. No actual real-device evidence, implementation, product decision or compatibility claim is supplied here.
