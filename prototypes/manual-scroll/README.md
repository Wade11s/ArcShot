# THROWAWAY — macOS Scroll Capture 实机探针

问题：[实机验证 Scroll Capture 的双向拼接、浮层捕获与输入协作](https://github.com/Wade11s/ArcShot/issues/15)。

**状态：原型已构建；没有完成真人 Scroll Capture 实机验收。不得据此关闭票据或锁定 V1 路线。**
资产只保留在 `prototype/manual-scroll`，不合并到 main。

## 一条命令启动

在本目录执行：

```bash
./run.sh           # 预览在选区右侧
./run.sh --inside  # 预览在选区内右下角
./run.sh --left    # 预览在选区左侧，测试窗口相应右移
```

首次构建需要联网下载 Cargo 依赖；运行期没有主动联网/本地端口的代码。
只面向当前 MacBook Air 单一内屏。不要打开真实敏感内容作测试。

启动后是 PREPARED 状态，**按 Start 才创建事件拦截并开始捕获**。测试目标是另一个进程的
原生 GPUI 窗口，不是浏览器/HTML，不是 ArcShot 的产品辅助进程。
固定目标窗口为 720×600 逻辑点，选区为其内部偏移 (16,16) 的 680×540 区域；
开始前根据 SCK 测得的实际窗口位置计算屏幕选区，并将同一个矩形交给输入拦截和采样。
窗口的请求初始位置不是捕获依据；采样开始后不跟随移动，位置/尺寸变化仍停止。
这是原型的固定夹具，不是产品选区交互，也不改变用户框选选区的产品规则。

`run.sh` 生成本地 ad-hoc 签名的 `target/ArcShotScrollPrototype.app`，
bundle ID 为 `dev.arcshot.scroll-prototype`。从终端直接运行，以保留纯文本诊断。
权限可能由系统归属到原型或启动它的终端；**记录实际设置页/提示中的名字**，
不要认为 bundle ID 已保证 TCC 身份稳定。重编译后可能需要重新授权。

## 真人测试：第一轮

1. 在系统设置 → 隐私与安全性中确认屏幕与系统音频录制、输入监控、辅助功能的实际授权。
   “Request screen/input permissions”按钮只请求前两项；辅助功能由人在设置页处理。
   授权后按系统要求退出并重新启动。程序不修改 TCC 数据、不绕过安全输入。
2. 在未采集时先单击彩色目标窗口，再滚动一下，确认终端有 `target_scroll`；
   其 `offset_points` 从 2000 开始。该次普通点击日志不算输入泄漏。
3. 按控制面板 Start。之后把指针移到目标的选区内，慢慢向下、向上、越过起点再向下。
   采集中面板鼠标穿透；只有选区内原始滚动放行，不合成/重发滚轮事件。
4. 看终端的 `verified_delta_px`、`result_height_px` 和 `fixture_*_ground_truth_exact`。
   成功判据不仅是“看起来连上”：位置应与目标日志相符，反向不重复，新内容可向上下扩展；
   ground-truth 必须为 true（夹具坐标条码解码后全图逐像素比较）。
   此 oracle 不决定匹配偏移，但源图真值不符会显式停止这个夹具专用测试。
   不能用这种专用真值保护推断任意 App 已具备同等目标身份/内容验证。
5. 先在目标上单击一次，再双击完成。采集中两次点击都不应出现
   `TARGET_RECEIVED_CLICK`。另开会话分别测试 Enter、Esc、Cmd-Shift-A。
   Enter/双击显式完成才编码 PNG 并写剪贴板；Esc 丢弃、保留固定选区；
   Cmd-Shift-A 丢弃并重新启动。正常结束会等待已拦截的控制键/鼠标释放再移除 tap。
6. 剪贴板只写 `public.png`；检查终端 `clipboard_png_write=accepted`，在你选择的应用中粘贴查看。
   粘贴或另存会将内容交给其他应用，是否保存由你决定。原型不自动保存任何截图。
7. 重启原型，用 `--inside` 重复测试，特别把指针放在覆盖于选区内的预览上滚动。
   再用 `--left` 测试。预览须不出现在捕获图中，其下内容必须仍正确、新鲜；
   只看到“没有浮层”不够，ground truth 和上下滚动的目标位移也须一致。
8. 每步报告“通过 / 不通过 / 未验证”和终端事实；人在场的操作/评价不能由自动 smoke 替代。

采集中其他普通键仍发送给目标，便于用夹具注入失败：`M` 改变内容、`B` 纯色、
`R` 重复内容、`U` 恢复唯一内容、`J` 跳过 1500 点形成缺口、`Q` 关闭目标。
期望显式停止；有已验证结果时只能由人按“Copy verified partial”输出。
纯色/重复夹具在初始帧就应拒绝。测试这些键前必须保证目标确实具有键盘焦点。
Esc/Enter 不应出现在目标键日志中。停止后单击控制面板、Cmd-Q 退出原型；
采集中焦点在夹具，Cmd-Q 可能先关闭夹具，这应被识别为目标失效。

## 候选路径与刻意限制

- 捕获：SCK display filter，排除 capture 进程的 application；显式 sRGB、
  sourceRect 逻辑点 → 输出物理像素，关闭光标。用 SCScreenshotManager.capture_image
  单帧请求循环取得完整 CGImage，再转换 BGRA；**一次最多一个未完成请求，没有持久 SCStream**。
  请求之间实验性等待 50 ms，不承诺帧率。记录请求序号/耗时、配置与返回图像尺寸，
  不伪称具有 SCStream 的完整帧附件/显示时间元数据。采样间隔不足以建立重叠时显式失败。
- 匹配：全宽行哈希枚举 ±75% 视口高度内的**唯一精确整数垂直位移**，
  再逐像素验证与整个已知连续文档的重叠；只向上下追加新条带。
  哈希不是最终验证；无候选、多候选、历史内容冲突均停止。
  此严格版本是保守探针，不是已经标定的通用/亚像素匹配器。
- 输入：main-runloop active Quartz session tap；点击/拖动返回 null，
  原始滚动原样返回；预览 NSWindow ignoresMouseEvents。不会转发给指定 PID，
  所以指针/焦点/系统路由仍须验收。tap 被禁用不自动悄悄恢复。
  按物理键/按钮记录 down 的归属，重复与 up 沿用；正常结束进入仅排空已拦截释放的状态，
  不用超时提前销毁 tap。系统禁用/安全输入导致保护丢失须显式失败，不能承诺无事件泄漏。
- 生命周期：worker 顺序等待单帧请求完成，没有 stream start/stop 或 stream delegate。
  任何截图请求失败/超时或 worker panic 都锁定输出和重启，要求退出重开；
  不对超时仍未确定的请求直接重试。run.sh 固定原生 completion timeout 为 30 秒；
  直接执行时也拒绝禁用/过大的超时配置。完成/取消时若单帧请求尚在途，回传图像将丢弃；
  新会话等待旧 worker 退出，旧请求不能输出。主线程写剪贴板。
  启动要求目标激活成功且是 foreground；主线程每 100 ms 检查焦点，丢失即停止。
  这是采样检查，不是系统路由的无竞态保证，仍须实机检验。
  定期检查目标 ID、on-screen、窗口几何、权限和单内屏拓扑。
  内屏/拓扑变化丢弃整个会话；其他失败只保留之前已验证部分。
- 实验上限：96 MiB 原始拼接图、180 秒；还存在请求/转换图、编码副本、预览、
  Metal/native 内存。记录进程 peak RSS、请求时间/序号、拼接及编码耗时。
  **这些值不是 V1 资源预算，不是完整峰值预算的证明**。
- 不实现完整菜单、真实全局入口、任意框选、标注、成功预览动画或全部产品恢复 UI。
  错误/取消后保留固定夹具选区，不代表正式选区状态机已实现。
- 尚不能证明所有受控自然内容兼容：此夹具使用整数物理像素、独特高纹理。
  任意 App、分数滚动、动态网页、固定浮层、低纹理、系统保留快捷键、
  其他窗口遮挡/嵌套滚动、保护内容都不能由此推断通过。

### 为什么最终没有使用 SCStream

初稿在代码审查中发现 screencapturekit 11.1.1 的 stop_capture 使用内部 capturing
标记短路返回 Ok；error trampoline 先清除此标记再调用应用 delegate，因此存在
“已报告停止成功，但应用错误回调尚未送达”的确认竞态。只检查应用错误 latch 或睡眠
不能消除该问题。为保持一个最小候选且不修改第三方桥，最终原型改用公开的单帧请求 API，
而不是为不确定的流停止放行自动输出。它的吞吐是否足以支撑手动滚动，必须实机证伪/验证；
此处不据此选定 V1 路线。

## 依赖与构建风险

本原型直接依赖 gpui 0.2.2（显式启用 font-kit）、screencapturekit 11.1.1；版本固定在 Cargo.lock。
另直接使用已在 GPUI 传递依赖中的 cocoa 0.26，仅复用 AppKit NSPoint 参数绑定以定位本进程预览窗口。
SCK 及 apple-cf 0.11.7、apple-metal 0.10.4 自带 Swift 源码桥接，由本机 Xcode 编译；
这是已允许的第三方构建例外，不是自有 Swift 桥，也**不代表产品已批准采用这些 crate**。
备选是 objc2-screen-capture-kit 原生 Rust 绑定，未在本原型并行实现。
GPUI 使用 Metal shader 原生编译；大量传递依赖含 HTTP 能力，但本程序不配置网络客户端/
远程资产源，不调用下载或端口 API。未进行运行期网络流量审计，不应把源码检查说成流量证明。

当前机器初始缺少 Metal Toolchain，已通过 Apple
`xcodebuild -downloadComponent MetalToolchain` 下载（838.9 MB，27A266a）。
第三方 Swift 桥初次链接缺少标准运行库 rpath；`build.rs` 只加入 Apple 的
`/usr/lib/swift` 运行库路径，没有打包第三方预编译二进制。
后续验证需确认原生 ABI、桥接维护与生命周期；GPUI 传递依赖
block 0.1.6 / proc-macro-error2 2.0.1 有 future-incompat 警告。

## 首轮真人反馈与原型修正

- 用户提供的控制面板截图显示：背景和按钮色块正常，所有文字均未显示。该截图仅在本机诊断，
  不随原型提交或上传公开票据。
- 已确认配置根因：关闭 GPUI 默认 features 也关闭了 macOS 的 `font-kit`，
  使框架选中 NoopTextSystem。现仅显式开启 `font-kit`，仍不启用无关平台默认项。
- 可运行的后端诊断：`./run.sh --probe-text`，不创建窗口/截图。用实际 Helvetica 的
  `i` / `W` advance 区分真实后端与空实现；修正前为 9.6 / 9.6 px，修正后为
  3.5546875 / 15.1015625 px。字体名称数量不是有效判据（GPUI 会追加 fallback 名称）。
  此诊断只证明选中了真实字体度量后端。用户随后已确认标题、权限和 Start 均可见；
  文字显示问题通过本轮用户复核，不等于捕获链路已经通过。
- 用户实际尝试启动时，日志多次出现目标不可见/选区不在目标窗口内，未进入采样；
  Esc 到达了夹具，而不是取消了 Capture Session。本轮滚动、Esc 不能算通过。
- 按同一 native window ID 比对，观察到 GPUI 正常逻辑 bounds 与 SCK 瞬时屏外缩略 frame
  不同；另一已激活窗口则两者一致。激活/桌面窗口管理过渡是候选解释，不宣称已证明 OS 根因。
- 第一轮仅增加了稳定等待，真人复测仍失败：同一窗口已经稳定在 (280,315,720,600)，
  原型却仍使用基于请求位置 (60,100) 的旧屏幕矩形 (76,116,680,540)。因此延长等待并不能解决。
- 现以相同 PID、layer 0、on-screen、完整夹具尺寸 720×600、同一 window ID+frame 连续两次稳定
  为准备条件，锁定身份后按实际位置计算相对选区；实测失败案例得到正确矩形 (296,331,680,540)。
  主线程先定位预览并将此矩形写入 tap，再以原子 ready 标志放行采样。准备时滚动不放行，
  取消/输入失败/握手超时均不采样；采样后仍检查锁定 ID/几何/焦点，绝不边采边跟随窗口。
  查询间准备预算 3 秒，单次系统查询仍受有限 completion timeout 限制，不是 3 秒硬墙钟上限。
  4 个几何回归用例通过；最终 native 采样、输入及取消还待真人复测。
- `./run.sh --probe-target <fixture-pid>` 只查询该夹具的窗口元数据并报告按实际位置计算的相对选区，
  不激活窗口、不截图；目标未处于正常可见状态时应失败。程序启动也记录本身的 native window ID。
  Warn 日志写终端，无自动图像落盘。
- 之前运行日志还记录过一次 cocoa 空引用崩溃；尚未建立稳定复现或证明修复，仍列为限制。

## 首帧像素失败：当前为诊断版，尚未修复

坐标绑定修正后的真人运行已完成目标准备与选区/输入握手：目标实际 frame 为
(162,206,720,600)，同一输入/捕获 ROI 为 (178,222,680,540)，scale=2，
返回 CGImage 为 1360×1080。首个单帧请求成功，但精确夹具 oracle 失败；
未接纳任何图像、未复制 PNG。用户已退出该次运行。

当前新增诊断只在原有 oracle 失败分支执行：
- 记录该 CGImage 的位深/行跨度，以及有界采样的方向、R/B 对调、小整数偏移误差统计。
- 对同一个已拥有的 CGImage 做显式 named-sRGB 提取作对照；没有追加截图请求。
- 映射搜索与归一化结果都**不参与接纳图像，不修改源图，不改变原有失败条件**。
  初始行 2016×scale 仅为无滚动夹具的诊断假设；报告亦尝试条码解码基点，不能把其输出当作来源证明。
- 只输出数值，不保存图像或写剪贴板；即使诊断映射得分为零，也继续按原校验失败停止。

无窗口/无屏幕权限的纯内存探针：
`./run.sh --probe-color` 创建自己的 sRGB CGImage，用旧 DeviceRGB 提取与 named-sRGB
提取作对照。当前两者均 5120/5120 像素精确一致，因此**没有证明 DeviceRGB 或行序是本次 native
失败根因**。该结果只检查这条生成图像路径，不证明实际显示合成/捕获无颜色变换或重采样。

当前 7 个测试覆盖几何、纯内存 sRGB 图像行序/颜色，以及诊断能识别人工翻转+通道交换
但仍不放行该图像。完整显示/捕获失败仍须用下一次真人触发的首帧诊断收敛，不应反复要求用户
测试一个被宣称“已修复”但实际尚未定位的问题。
